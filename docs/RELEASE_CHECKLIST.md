# MailPilot 发布验收清单

每次在独立测试项目中使用专用邮箱、Telegram Bot、私聊和合成邮件验收。当前部署每个环境选择一种邮箱提供商。先验收 Gmail，再在获授权的 Outlook 测试环境用同一候选版本复测，两个渠道分别登记结果。

## 需要项目所有者完成的事项

1. 确认要发布的提交、目标 GCP 项目、允许使用的模型及 Telegram 私聊，批准测试项目的部署和通知配置。推送前确认变更范围，然后从 GitHub 的 **Actions → Deploy MailPilot → Run workflow** 选择 `main`。若启用紧急提醒，按部署手册单独应用通知和补扫配置。需要在生产环境处理真实邮件时，先确认学校和模型服务的数据处理条件。 [部署手册](DEPLOYMENT.md)
2. 在独立 Gmail 测试账户完成浏览器授权。若既有授权仍有效，可复用。为 Outlook 提供可授权的 Entra 租户与桌面应用、专用账号以及委托 `Mail.Read` 和离线授权所需同意。若学校租户无法同意，保持 Outlook 的真实验收待办。
3. 在测试私聊依次验证 `/help`、`/digest`、`/detail 1 3`、`/translate 1 3`、`/filtered`、`/rules` 及按钮。准备至少两页合成邮件，打开新批次后再点击旧批次按钮。确认编号、页和邮件匹配，并在获准的另一个测试账号上检查未授权请求不返回邮件数据。
4. 按本轮安排在上线后观察首个苏黎世 21:00 自然调度。记下本地日期、实际送达时间和是否重复，只回报结果或脱敏编号。次日 06:00 使用相同方法。运维人员用这两个时点关联 Scheduler、Worker、Job 和 Telegram 的证据。
5. 若以开源方式发布，确认项目许可证及适用的第三方署名。当前仓库尚无根许可证文件，许可证选择由项目所有者决定。

## 调度、缩零与参考负载

- 在 Scheduler 运行历史定位自然触发，记录固定时段、计划时间、Worker 请求结果和 Job 执行名。通过批次短 ID 核对只确认一组 Telegram 投递。21:00 按本轮安排延后，验收栏保留待核对。
- 在 Cloud Monitoring 按服务与承载流量的 revision 查看 Cloud Run 容器实例数（`run.googleapis.com/container/instance_count`）。记录 UTC 空闲窗口，保留活跃和空闲实例均为 0 的证据或能证明归零的服务观测；独立记录随后冷启动首个请求。无数据点时标为待验证。核对期间避免主动探活请求干扰窗口。
- 用三个已完成回填的测试账户发共 30 封合成邮件。Outlook 参考配置为每账户八个跟踪文件夹，Gmail 为每账户一个邮箱级游标。在确认没有积压的情况下运行定时摘要，记录 Cloud Run 执行开始与完成时间、应用的 `seconds`、账户数、同步页数、邮件数、模型请求、重试和 `pending_accounts`。正常样本以成功退出、至多 300 秒和零待补收验收；积压恢复结果单独记录。

## 紧急提醒、续期与补扫

1. 每家分开收集至少 40 封由正常 SMTP 投递的合成邮件，每封预先分配一个测试编号，至少 10 封对应已观测到当前环境从零启动的请求。邮件主题使用已确认会触发紧急规则的固定模式，保持正常负载并避免人为批量重试。
2. 用 Gmail `internalDate` 或 Outlook `receivedDateTime` 作起点，关联 `email_wake` 的任务短 ID 和 `email_urgent_result` 的邮件短 ID。记录提供商收件、通知接收、任务开始、分类完成、Telegram 发送确认 UTC 时刻，以及 `channel`、结果和冷启动标记。计时使用确认事件的 `latency_seconds`。未确认样本记为失败且单列数量，即使后来通过补扫送达也以其实际确认时间和渠道另行记录。
3. 对数据按延迟升序取第 `ceil(0.95 × N)` 个值，始终使用已发送测试邮件总数作为 `N`，未送达样本按无穷大排序。每家报告样本数、P95、超过 120 秒和未送达数量、失败率、冷启动样本数及重复投递数。仅凭成功样本的 P95 无法关闭此项。
4. 确认 watch 或订阅过期时间实际延长。记录 Gmail 日续订、Graph 剩余不足 48 小时续期前后的 `renewed_at`、`expires_at` 和状态。另行演练一次推送中断，仅在独立测试环境启用补扫模式，保留原游标并发送合成邮件。至少覆盖一种紧邻巡检完成的投递，使等待接近 15 分钟。记录下一次巡检计划、`channel=poll` 及确认时间，健康环境目标 17 分钟内。恢复推送后验证后续来信走原渠道，已确认的邮件仅投递一次，摘要显示「已提醒」。 [通知配置与恢复](DEPLOYMENT.md#紧急邮件通知与翻译)

## 幂等、隐私与恢复

- 在专用测试环境复用同一个已登记批次 ID 重跑；用相同模拟更新和任务 ID 核对已确认分段。真实环境遇到 `UNKNOWN` 时按运维流程核对聊天和投递记录。
- 预先在合成正文、附件和预期译文中分别放入唯一占位标识。在受控环境核对 Firestore 邮件、任务和投递等文档、Cloud Tasks 请求正文、Cloud Logging 和 CI 工件无这些完整材料及凭据。记录检查覆盖的集合、队列、时间范围、CI 运行及命中数量。保留有限的流水元数据、计数和脱敏编号，避免导出原始负载和日志。
- 暂停并恢复测试调度和队列，核对旧镜像、配置及 secret 版本仍可使用。以同一批次、回执和游标确认恢复没有丢失状态。云配置与版本操作见部署手册。 [轮换与回滚](DEPLOYMENT.md#轮换与回滚)

将每项标为通过、失败或待测，并记录欠缺证据、负责人和恢复条件。发布操作由项目所有者授权。
